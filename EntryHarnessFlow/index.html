설명을 위해 줄인 예문입니다. 실제 요청은 더 자세했고, 플레이 검증까지 포함했습니다.

실제 제작 때 보낸 요청은 이렇게 더 자세했습니다. 프로젝트의 지식과 도구를 쓸 것, 커브·언덕·라이벌 차·랩타임, 순수 엔트리 블록만으로 동작하는 .ent 파일, 그리고 실제 플레이 검증까지 끝내고 보고하라는 조건이 들어 있었습니다.

기존 도구

이 그림이 작품의 핵심 구조입니다. 맨 위는 Codex나 Claude Code 같은 기존 AI 에이전트, 맨 아래는 공개된 엔트리 엔진입니다. 둘 다 기존 도구이고, 엔진 소스는 고치지 않았습니다.

제가 만든 것은 가운데의 엔트리 하네스입니다. 지식·작업 지침, 명세·생성 도구, 편집기 연결, 실행·검사 도구 네 부분으로 이루어져 있습니다.

AI는 하네스의 도구를 실행하고, 하네스는 오류와 상태를 AI에게 돌려줍니다. 아래로는 작품과 키 입력을 엔진에 넣고, 엔진의 상태·화면·소리를 받아 옵니다.

정리하면, 게임을 어떻게 움직일지 정하고 고치는 판단은 AI가 하고, 형식 변환·실행·검사는 도구가 맡습니다.

(마지막) AI가 고친 명세는 다시 1단계부터 같은 과정을 거칩니다. 다음 장부터 한 단계씩 자세히 보겠습니다.

03 · 제작 과정

    ① AI가 게임 동작을 중간 명세로 씁니다

    AIAI 에이전트게임 동작을 정하고 명세로 작성

    이 10줄에 담긴 동작

    DSL — 엔트리 블록 명세를 쓰기 쉽게 만든 작성 함수입니다. 이 명세가 검사를 거쳐 엔트리 블록이 됩니다.

    첫 단계는 AI가 게임 동작을 중간 명세로 쓰는 일입니다. 엔트리 작품 파일은 블록 데이터와 그림·소리가 겹겹이 묶인 구조라서, AI가 쓰기 쉬운 작성 함수, 즉 DSL을 준비했습니다.

    화면은 실제 SUNSET DRIVE 명세의 10줄입니다. 위쪽 화살표나 Z를 누르면 속도를 올리고, 아래쪽 화살표나 X는 브레이크, 좌우 화살표는 좌우 위치를 바꿉니다. 왼쪽 버튼을 눌러 바로 골라 볼 수도 있습니다.

    무엇을 어떻게 움직일지는 AI가 정합니다. 이 명세가 다음 단계의 검사를 거쳐 엔트리 블록으로 바뀝니다.

      생성 명령도 같은 검사를 먼저 거쳐, 오류가 남은 명세로는 .ent를 만들지 않습니다. 게임이 의도대로 움직이는지는 ④ 실행·관찰에서 확인합니다.

      두 번째는 정적 검사입니다. 중요한 점은 작품 파일을 만들기 전에, 실행하지 않고 명세 파일만 읽어서 검사한다는 것입니다.

      엔트리에 실제로 있는 블록인지 474종 블록 목록과 대조하고, 입력 칸의 개수와 값의 종류, 선언된 변수·함수·오브젝트를 제대로 가리키는지 확인합니다.

      통과하면 작품 생성으로 넘어가고, 오류가 있으면 위치와 이유를 보고해서 AI가 명세를 고칩니다. 생성 명령도 이 검사를 먼저 거치기 때문에 오류가 남은 명세로는 작품 파일을 만들지 않습니다.

      다만 게임이 의도대로 움직이는지는 이 단계에서 알 수 없어서, 뒤의 실행·관찰이 필요합니다.

                05 · 정리

                판단은 AI가, 확인은 하네스의 도구가 맡습니다

                1. 1

                  기존 도구를 잇는 하네스

                  AI 에이전트와 엔트리 엔진은 기존 도구를 쓰고, 그 사이의 지식·명세·생성·실행·검사 도구를 만들었습니다.

                2. 2

                  만들기 전에 검사, 만든 뒤에 실행

                  명세 작성 → 정적 검사 → 작품 생성 → 실행·관찰 → 작품별 검사 → 피드백

                3. 3

                  고치고 다시 확인

                  AI가 오류와 상태 보고를 읽고 명세를 고친 뒤 다시 검사합니다. 실제 제작 기록에서도 이 반복이 있었습니다.

                자동 검사는 정해 둔 항목을 확인합니다. 모든 게임의 완성이나 성공을 보장하지는 않습니다.
